# ADR-0002: Open-core purpose-bound information protection (experimental)

**Status:** Proposed, experimental attested reference implementation; no production security or PCI compliance claim.
**Owner:** QualityRAG / Dodo LLC
**Date:** 2026-11-06

## Decision

Keep the QualityRAG evidence engine, PackSpec contracts, semantic grammar research,
SDKs, conformance tests and basic masking/reference protection open source
under the repository's existing Apache-2.0 license. Implement a **pluggable
commercial enforcement plane** later, without closing the core formats.

The initial Python reference modules are `sdk/python/qualityrag/protection.py` and `sdk/python/qualityrag/protection_attestation.py`.
It selects purpose-scoped views from **already protected** source records.
It never accepts, stores, encrypts or detokenizes raw payment card data.

### Data flow

1. A trusted resource service classifies every field and produces protected
   references plus independently verified safe derived attributes.
2. The reference selector checks schema, tenant, subject, purpose, destination,
   field classification, operation, and explicit grants.
3. Unknown field classifications, unsupported modes and raw sensitive
   values fail closed. Unrequested fields are omitted.
4. The model sees an approved view only.
5. A future independent outbound enforcement service authenticates release
   receipts and rechecks destination policy before executing any action.
6. A separate privileged vault handles necessary detokenization without
   providing the raw value to the model.

### Critical limitations of the reference prototype

- `authenticated: true` is a **caller assertion**, not a signature check.
  A caller cannot trust this assertion from untrusted sources. The caller
  MUST authenticate resource contracts independently before calling `protect`.
- The `authorize_release` function checks policy fields but its input is
  not cryptographically authenticated. **Never expose this function as a
  security boundary or call a real outbound service based on its answer.**
- Regex PAN rejection is only a last-resort defensive check, not comprehensive
  discovery of cardholder data, PII, PHI or unstructured attachments.
- Safe attributes (including last four) may still be regulated or identifying
  in combination with other data. An authoritative resource must establish
  that the field is permitted for this particular purpose.
- References generated by external vaults must be non-redeemable outside
  their authorized vault context. This prototype does not mint tokens.
- No field encryption, FPE, cryptographic proofs, policy signatures, revocation,
  replay protection, KMS/HSM, real payment execution, retention controls,
  security telemetry, or PCI scoping assessment is implemented.

### Commercial extension interface (planned, not implemented)

A deployable proprietary edition could provide:
- production authenticated resource provenance and immutable policy versions;
- trusted vault/KMS adapters and tenant-bound reference minting;
- identity federation and least-privilege capability issuance;
- production signed, short-lived, distributed replay-resistant outbound release receipts;
- purpose/operation/destination-scoped authorization with revocation;
- detailed non-sensitive audit evidence, monitoring and support;
- testable controlled-release behavior across cloud/agent boundaries.

The reference contract and conformance scenarios remain public so that
open-source implementations can compete and interoperability survives.

## Product hypothesis and acceptance gates

**Hypothesis:** A purpose-aware protected representation can expose less
information than generic masking/tokenization while preserving task utility.

Test on exclusively synthetic contracts and payment records against
(a) conventional masking, (b) tokenized references with approved attributes,
and (c) a purpose-scoped representation. Evaluate correctness, leakage
(including composition across attributes), cross-tenant violations, injection,
inference, cost and latency. Negative outcomes must be retained.

### Before production or sales claims

- Independently verify signatures and contract provenance; reject unsigned
  or untrusted classifications. No client-controlled boolean trust shortcut.
- Audit non-structured ingestion including PDFs, OCR, logs and model traces.
- Implement a real isolated vault and per-tenant cryptographic separation.
- Bind release decisions cryptographically to authenticated identity,
  purpose, audience, operation, expiry and nonce.
- Demonstrate replay, confused-deputy, privilege escalation and prompt
  injection denials in independent adversarial tests.
- Obtain the appropriate PCI DSS scope assessment; do not claim that
  tokenization alone removes a system from scope.
- Validate buyer demand and a paid pilot before committing the IP boundary.

## Follow-on implementation (synthetic evaluation)

- `sdk/python/qualityrag/protected_metadata.py` defines a metadata-only
  `ProtectedMetadataProvider` API and a synthetic in-memory implementation.
  There is deliberately no `decrypt`, `reveal`, or `detokenize` method;
  the interface is not a payment vault, credential store, or transaction API.
- `examples/protection_comparison.py` includes deterministic, synthetic
  redaction, tokenization-plus-attributes, and purpose-scoped comparison
  fixtures, with regression tests. The redaction/tokenization policies are
  selected baselines, not state-of-the-art or comprehensive provider
  implementations. Field counts are not entropy, inference leakage, or
  privacy metrics.
- Real evaluation must include held-out authorized tasks, false-positive
  and false-negative sensitive-field classification, joined-attribute
  reidentification, utility preservation, leakage attempts, and operational
  overhead. Publish failures and cost measurements with the results.
- Existing raw-caller `protect` and `authorize_release` APIs remain
  **demonstrations only**. Refactoring them into strictly private/internal
  helpers and strengthening externally authenticated entrypoints is required
  before any service integration.

## Policy revision and revocation prototype

The experimental attestation path now requires signed `policy_id` and
`policy_version` in its contract. A trusted `InMemoryPolicyAuthority`
tracks the active version for each tenant and policy. Both view issuance
and release verification require that the signed version is currently active.
Publishing a new version invalidates receipts created under older versions;
revocation invalidates outstanding receipts for that policy.

The registry retains a monotonic version high-water mark when a policy is
revoked, so the prior revision cannot simply be republished. Test coverage
includes revocation between issuance and release, downgrade attempts, and
cross-tenant policy confusion.

**Important:** this is not durable or distributed revocation. Multiple
processes would hold inconsistent views and restarts would lose history.
The registry must never be passed into a real trusted service by a request
caller. Production needs an authenticated central policy authority,
persistent monotonic versions, a failure-closed lookup, and race handling
between revocation and actual delivery. It also needs independently
authenticated workload identity. The current `Principal` remains a
caller-provided test object.

## Authenticated-workload service boundary (experimental)

`sdk/python/qualityrag/protection_service.py` implements an in-process
`ProtectionService` facade whose issue and release methods accept a signed
workload assertion rather than a caller-constructed `Principal`. A
`SignedWorkloadVerifier` checks its MAC, configured key identifier,
issuer, audience, subject, tenant, purposes, issue time and expiration.
The service derives its own `Principal`, holds the signing keys on the
service side, checks policy versions, and consumes one-time receipts.

This example uses synthetic HMAC assertions to exercise the trust model.
**It is NOT OIDC, JWT, OAuth, SPIFFE/SPIRE, mTLS, or production authentication.**
A trusted IdP adapter must replace it before network exposure. Assertions
must be obtained through an authenticated transport and identities must
be mapped to organization-approved, server-side authorization grants.
Anyone able to mint a valid assertion with a trusted key can impersonate
an authorized workload; keep keys out of model contexts and untrusted
runtime processes. The public `sign_synthetic_workload` helper is test
infrastructure only.

Still required: durable and atomic distributed policy state, replay
database, identity revocation and key rotation, signed key provenance,
audited administrative operations, and a real isolated vault boundary.
Successful SDK tests are correctness checks, not security accreditation.

## Independent workload authorization

`protection_grants.py` defines server-owned `StaticWorkloadGrants`:
the verified identity assertion establishes who is calling, but only
a separately configured grant permits its specific tenant, subject,
purpose, and destination. The `ProtectionService` requires these grants
both before issuance and before release. A signature indicating more
purposes than the service has granted confers no extra privileges.

The static grant set is test infrastructure, not a production policy
decision point. A production deployment requires authenticated
administration, durable grant state, tenant-scoped revisions, and
revocation consistency. The trusted service must construct its grants
and verifier internally; never let an untrusted caller supply their own.

## Durable policy / replay persistence (experimental SQLite)

`sdk/python/qualityrag/protection_sqlite.py` adds `SQLitePolicyAuthority`
and `SQLiteReplayStore` using SQLite transactions and a shared database
file. They conform to the policy/replay protocols used by the attested
protection service. A policy's highest version survives revocation and
restart, avoiding accidental downgrade. Nonce insertion uses a unique key
and an immediate transaction, so concurrent processes sharing that database
cannot both consume the same nonce. Synthetic service and concurrency tests
cover both behaviors.

**Operational boundary:** These stores are suitable for local development
or controlled single-host evaluation only. They are NOT proof of globally
consistent authorization in an elastic multi-host deployment. Production
requires a properly authenticated and monitored central policy registry,
trusted time, key rotation, database backup/recovery, tenant admin
authorization, distributed nonce retention, failure-mode tests, and an
atomic release decision tied to actual outbound delivery.

SQLite on an unreliable network share is unsupported. Do not accept the
database path from requests. Access-control on the DB itself must be
enforced outside this code. Anyone who can directly modify these tables
can bypass the protection policy. This prototype neither ingests nor
stores real PAN values.

## Atomic database release decision

`SQLitePolicyAuthority.consume_if_active(...)` now combines current-policy
version lookup, revoked-policy rejection and one-use nonce insertion under a
single `BEGIN IMMEDIATE` SQLite transaction. The attested release verifier
calls this method when the configured policy authority provides it, instead
of performing separate policy checks and nonce updates. Regression tests cover
duplicate attempts, revoked versions, tenant isolation and competing
revocation/claim operations. In-memory test registries retain their earlier
non-atomic behavior and must not be deployed as security boundaries.

**What the transaction proves:** inside a single correctly locked SQLite
database, a completed policy revocation is observed by a later release
claim, and only one concurrent claim for a given nonce succeeds.

**What it does not prove:** if revocation commits *after* a claim but before
an external API call completes, that external disclosure could still occur.
Do not claim strict revocation-at-delivery or exactly-once delivery. A
production disclosure component requires an authenticated outbound proxy,
revalidation at the point of delivery, authoritative policy state, and a
carefully specified response to retries, partial failures, timeouts, and
cancellation. No external disclosure is performed by the current code.
